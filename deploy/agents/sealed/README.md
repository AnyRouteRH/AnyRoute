# Sealed agent hosting recipe

Run an owner's digest-pinned agent and the Anyroute agent sidecar inside an Intel TDX dstack confidential VM. This recipe is available for self-hosting; sealed-agent registration is not switched on yet. Measured code is not audited code. The owner approves the exact manifest and both image digests before registration.

Build from the repository root with `docker build -f deploy/agents/sealed/Dockerfile -t agent-sidecar .`, publish the resulting image using your own release process, and resolve its immutable registry digest. The Dockerfile needs no package installation. Its default root user is confined to the guest and is needed for its guest socket and sealed volume; never expose a guest administration interface as the agent API. Provide `AGENT_IMAGE` and `AGENT_SIDECAR_IMAGE` as `registry/image@sha256:<64 lowercase hex>`, `AGENT_IMAGE_DIGEST` as the matching `sha256:<64 lowercase hex>`, the dedicated non-management key's `AGENT_KEY_HASH` (SHA-256 of the credential), and `AGENT_ATTEST_HOSTNAME`. Only the fingerprint belongs in the manifest. `AGENT_ROUTER_ORIGIN` is an HTTPS origin and defaults to `https://anyroute.tech`.

Materialize the template from the repository root with `bun deploy/agents/sealed/render.ts > docker-compose.yml` and review the resulting manifest. The renderer refuses mutable images and image/digest mismatch, and accepts only the listed non-secret settings. `AGENT_IMAGE_DIGEST` may be omitted because the renderer derives it from `AGENT_IMAGE`. Deploy those exact bytes through the dstack confidential VM workflow. Both images must be pinned, the agent's network must remain internal, only the sidecar's attestation port may be published, and the agent must not mount the guest socket or sealed volume. Do not add host mounts, privileged mode, host networking, downloaded startup code, or plaintext credentials. Review the container entrypoint as well as the image; all executable code and mounts affect the trust decision. The agent must support the configured OpenAI base URL without requiring the actual Anyroute key. An agent may send a non-secret bearer label to the internal proxy; it is discarded.

Provision the dedicated API credential over the platform's authenticated confidential guest console, through stdin to `docker compose run --rm -T sidecar provision`. Feed it directly from your secure provisioning channel, without placing it in shell arguments, history, compose YAML or an environment file. Confirm the guest's hardware evidence and measured manifest through an independently trusted verifier before provisioning; the confidential console and its operator are part of your trust boundary. The sidecar fails startup until the sealed file exists. After provisioning, restart the sidecar and agent. No remote provisioning endpoint is exposed.

The guest agent's `/GetKey` derives an application-scoped key with a path including the platform-reported compose hash and a versioned sealing domain. AES-256-GCM seals the credential in `/sealed/api-credential.bin`, with the compose hash authenticated as associated data. Restarts of the same measured app recover it. This sidecar derives a different sealing path when the measured compose changes and refuses recovery with that key; upgrades require fresh provisioning. GetKey paths are caller-selected, so path separation alone is not KMS access control: replacement code given the same application key could request a previous path. Use a fresh dstack app identity for every changed manifest, and authorize only the approved measurement in KMS; never grant a replacement measurement the old application key. KMS authorization must restrict release to approved dstack measurements. Application identity, KMS policy, guest OS and encrypted-disk configuration remain operator responsibilities. Deleting or losing the sealed volume loses the credential; restoring an older volume can roll back secrets. JavaScript credential strings cannot be reliably erased from process memory.

Obtain the measured compose hash from the dstack deployment evidence (not a hash of an interpolated fragment). With the principal's Bearer credential, register:

```http
POST /api/v1/agents/{key_hash}/sealed
Content-Type: application/json

{"attestation_url":"https://agent.example:8443/attest","agent_image_digest":"sha256:<digest>","compose_hash":"sha256:<measured-compose-hash>"}
```

The router requires `AGENT_SEALED_ENABLED=true` (default false), `AGENT_POLICY_ENABLED=true` (default false) and a configured `dstack` or `phala` quote verifier in `ATTESTATION_VERIFIERS`. Keep the existing attestor worker enabled. A fresh quote commits canonical JSON of the image digest, measured compose hash, SHA-256 key fingerprint, sidecar version and TLS SPKI hash, followed by the router's 32-byte nonce. All configured verifiers must accept it; one must recover the expected measured compose hash. Debug-enabled TDX and software evidence are refused. The TLS connection accepts exactly the certificate whose key the quote commits. The agent list and `/api/v1/agents/me` expose success only while fresh; failures clear it, and badges expire after 30 minutes even if the worker stops. DELETE the same registration URL to remove it.

The internal proxy only forwards chat completions, encrypted chat completions, embeddings, model discovery, agent self-description and rulebook checks to the configured Anyroute origin. It streams bodies and responses and preserves receipt, lane and policy headers. The API key is unavailable to the agent container, but the sidecar necessarily sends it to Anyroute as HTTPS Bearer authentication. The credential's owner may retain another copy; the badge does not prove exclusive possession or that each subsequent API request originated in this VM. Attestation proves a measured deployment held a matching credential when checked, not the agent's behavior or safety.

TDX, firmware, quote-verifier services, the dstack guest OS and KMS are trusted. Guest administrators and code inside this measured VM can access its secrets; attestation does not prevent exfiltration by owner-approved code, denial of service, rollback or all side channels. Ordinary requests sent to Anyroute are read by its router in memory on every lane. The encrypted-chat path can keep message plaintext off the router when the agent explicitly uses that transport; sealed hosting alone does not enable it. The sidecar reads and forwards agent request bodies in memory and stores no prompts or answers.

Guest API reference: [dstack GetKey](https://github.com/Dstack-TEE/dstack/blob/next/sdk/curl/api.md).
